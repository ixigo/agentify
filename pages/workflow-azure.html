From the board to a draft PR, hands-off.

Install the workflow once. After that you opt a work item in on Azure Boards, and the agent triages it, picks it up, implements it in an isolated worktree, checks reviewer conventions, and opens a draft Azure Repos pull request — all driven through the az CLI.

One-time setup

Install the Azure DevOps workflow

From inside the repo, agentify workflow install detects Azure DevOps from your git remote and lays down the skill bundle. You need the az CLI with the azure-devops extension and an active sign-in first — the workflow checks the extension and az account show before it touches anything.

# add the azure-devops extension, then sign in
az extension add --name azure-devops
az login

# from the repo: auto-detects Azure DevOps from the remote
agentify workflow install          # or: agentify workflow install azure
agentify workflow install

What your agent does on its own

Four moves take a shaped work item to a draft PR. You only do the first — opt the item in. Each move is a skill in the bundle; the agent runs them in order.

01 · Triage

Opt a work item in

azure-devops-triage inspects work-item fields, comments, states, and tags with az, then recommends changes rather than assuming them — Azure Boards process templates vary. It maps the opt-in state onto whatever active state your template uses (New, Active, To Do, Committed), and tags an item with agentify-ready only when your project already uses tags. A rough item gets shaped first — grill-me asks one question at a time until it is concrete, then files it with az boards work-item create.

02 · Pick it up

Load the work item as a checklist

ado-autopilot resolves org, project, and repository from the Azure Repos remote or az devops configure defaults, loads the item with az boards work-item show --id <id> (or a PR with az repos pr show), and turns it into an execution checklist.

03 · Implement

Work in an isolated worktree

worktree-autopilot cuts a fresh branch and git worktree off the right base, makes the smallest change that fixes the item, and verifies it with the repo's own formatting, linting, type checks, and tests. It commits with a conventional message and leaves your checkout untouched.

04 · Raise it

Check conventions, then open a draft PR

First pr-convention-learner scans the changed files against the repo's accumulated .conventions/conventions.md and flags violations — must-fix for high-confidence rules, consider for the rest — so recurring review nits get fixed ahead of time. Then pr-creator re-checks az, the azure-devops extension, and sign-in, confirms the base and source branch, title, and body, and opens a draft PR with az repos pr create --draft true. Nothing is marked ready for review unless you ask.

You never invoke it by name. You don't type skill names or call a command per step. You describe what you want — "triage the board", "pick up that work item", "open the PR" — and the matching skill activates from its description. Opt the item in; the agent takes it from there.

A day with the workflow

A bug lands on the board. You spend a minute on it; the agent spends the rest.

  1. Someone files a vague work item. You run a grilling pass until it is concrete, then move it to an active state (and tag it agentify-ready if your project uses tags).
  2. You say "pick up the ready item." The agent loads it, branches into a worktree, implements and verifies the fix.
  3. It checks the changes against learned conventions, opens a draft PR, and drops the link in the thread. You review, nudge, and mark it ready when you're happy.
What the bundle installs

Eight skills, templated for your provider: azure-devops-triage (inspect Boards fields, states, and tags), grill-me (shape a new item, then file it with az boards work-item create), ado-autopilot (resolve work item/PR context with az), issue-killer (fan opted-in items out to parallel tmux worktrees), worktree-autopilot (isolated implement, verify, commit), pr-convention-learner (pre-PR check against learned reviewer conventions), pr-creator (draft PR with prerequisite checks), and commit-creator (focused, conventional commits).

Run several at once

When more than one work item is opted in, issue-killer launches one tmux pane and one worktree per item from an az boards query --wiql tag filter, each agent opening its own draft PR. Watch them with tmux attach -t issue-killer. Hand-offs are recorded with agentify ctx note, and every worktree gets its own .agentify/ store, so notes stay per-checkout.

States and tags on Azure Boards

Process templates differ, so the workflow recommends changes after inspecting existing field values — never assumed — and preserves existing tags. The opt-in "ready" state maps onto an active, non-terminal state such as New, Active, To Do, or Committed, and the agentify-ready tag is used only when the project already works with tags or you ask for it.

Push options and guardrails

Draft by default: nothing is marked ready for review automatically, and non-draft PRs happen only when you ask. No force-push, and no closing work items, completing PRs, bypassing policies, or mutating state on your behalf. Work items are chosen by the opt-in tag or explicit IDs, PATs are never stored in skill files or commits, and every triage comment carries an AI-generated disclaimer at the top.

Board queries you can run 
# readiness
az extension show --name azure-devops
az account show
az devops configure --list

# the opted-in board
az boards query --wiql "SELECT [System.Id], [System.Title] FROM WorkItems \
  WHERE [System.Tags] CONTAINS 'agentify-ready' AND [System.State] = 'New'" -o json

# load one work item as a checklist
az boards work-item show --id <id>
If something's off

“Unknown command: workflow” — update Agentify with the installer and open a new terminal. No platform detected — the remote isn't Azure DevOps, or there's no origin; pass it explicitly with agentify workflow install azure. Extension missing — run az extension add --name azure-devops and az login, then re-run the install.
